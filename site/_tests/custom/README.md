# Custom worked examples

Three landing pages produced by the custom route, the path a build takes only when the user asks for it ("custom", "derive it", "bespoke", "no theme"). A custom run never deals a theme and never borrows a theme's faces, palette or signature: it names and rejects the category's reflex aesthetics, writes a slate of seven grounded directions, lets `scripts/seed.mjs` draw one and deal three challengers, sets the light with a scene sentence, declares a colour posture, and writes a five-block direction contract into the stylesheet that the finish review audits promise by promise.

These three were once the worked examples inside the ritual file. They were cut from the reference (three invented brands are copy-paste bait inside a file the model reads at build time) and kept here as rendered HTML so a constructed palette and pairing can still be inspected. They predate v2 and show the earlier gates.

## What keeps a custom run from inventing freely

1. **The catalog is a rejection table, not a menu.** `theme.mjs check --axes --face --hue` refuses a triple a theme owns, a display face a theme sets, and an accent within 20 degrees of a neighbour on the same paper and display class.
2. **The draw is external.** `seed.mjs` hashes the brief, the date and the run index to pick which slate entry gets built, because a model's own ranking returns the same favourite every time.
3. **Every gate applies unchanged.** A custom run has no waiver a catalog run lacks.
4. **The Picks block surfaces everything before code**: the draw, the challengers, the palette, the pairing and the contract, in plain text, so the user can redirect early.
5. **Rotation is route-blind.** Each run records its axes in `.hallmark/log.json` and the next run rotates against it either way.
